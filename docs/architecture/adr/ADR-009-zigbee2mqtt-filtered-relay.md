# ADR-009: направленный MQTT connector с сохранением происхождения показаний

Статус: **принято 1 октября 2026 года**.
Владелец разрешил реализацию словами «Можешь менять код» после предложения
исправить MQTT-мост по этому ADR. Развёртывание выполняется совместимо,
без автоматического изменения локальных установок пользователей.

## Контекст

Существующий connector в `zigbee_coordinator/connector` использует два
Mosquitto bridge и шаблон `+` для имени устройства. Zigbee2MQTT допускает
имена с `/`, например `garden/nested`, однако их state, availability и
обратные команды не проходят через текущий шаблон. `bridge/devices` при этом
приходит, поэтому устройство выглядит добавленным без работающих показаний.
MQTT-адаптер backend также игнорирует state с `/`.

Вторая проблема касается сохранённых показаний. При первом соединении
connector получает старое retained-состояние локального broker. Подписчик
GrowerHub получает его как новую публикацию с RETAIN=0. Backend различает
сохранённый snapshot и живое состояние по этому признаку, поэтому прежнее
показание может обновить время живого состояния без нового измерения.

Обе проблемы воспроизведены на официальных исходниках Mosquitto 2.0.22,
версии опубликованного connector. Использовались три тестовых broker внутри
отдельного сетевого namespace без доступа к production и физическим
устройствам. Сборка без TLS проверяет маршрутизацию, а не Docker-образ или
production TLS. Локальная проверка подтвердила потерю вложенного state и
признака сохранённой доставки при статической пересылке.

Общее `topic #` пересылает также команды и служебные данные и не является
подходящим исправлением. Статический список точных имён требует обновлять
конфигурацию после добавления и переименования устройств. Переименование
рабочих устройств Home Assistant не решает причину.

Решение дополняет ADR-002 и ADR-007. Оно изменяет формат передачи данных
connector, поэтому требует отдельного согласования по `AGENTS.md`.

## Решение

### Один connector и прежняя настройка пользователя

В существующем `zigbee_coordinator/connector` статический broker bridge
заменяется техническим процессом с двумя MQTT-соединениями: локальным и
облачным. Отдельного приложения, backend-домена или альтернативной истории
устройств нет. Backend остаётся источником бизнес-истины.

Connector получает `bridge/devices` и держит только производный список
полных friendly name. Добавление, удаление и переименование автоматически
обновляют разрешённые маршруты. Неоднозначные пересечения имён с маршрутами
команд или availability отклоняются с понятной диагностикой; пакет не
направляется предполагаемому устройству.

Пользователь по-прежнему задаёт адрес своего broker, порт, base topic и
локальные credentials, скачивает личную конфигурацию и запускает Docker
Compose. Вместо `bridge.conf` новый пакет получает структурированный
`connector.json`. Конфигурацию формирует существующая общая форма мастера и
настроек. Локальные credentials остаются только у пользователя и не входят
в REST, аналитику, журналы или исходящие metadata.

Облачное соединение использует существующие TLS, проверку сертификата,
MQTT credentials, namespace и client ID координатора по ADR-002. Локальный
client ID сохраняет суффикс `-local`. Изменения credentials рабочей фермы
или её Zigbee-сети не требуются.

### Явный контракт данных из локального broker

Для нового connector вводится только исходящий маршрут:

```text
<base_topic>/bridge/relay/<исходный относительный Z2M topic>
```

Каждый исходный topic сохраняет собственный маршрут и retained snapshot;
состояния разных устройств не записываются в один общий retained topic.
Payload имеет следующий формат:

```json
{"v":1,"payload":"{\"temperature\":24}","retained":false}
```

`payload` — исходное сообщение, `retained` — признак сохранённой доставки,
полученный connector от локального broker. Версия, типы полей и размер
проверяются на границе MQTT. Identity координатора берётся из защищённого
namespace, а не из JSON. Неизвестный формат не обрабатывается как обычный
state. Итоговый признак сохранённой доставки равен логическому OR между
внешним MQTT RETAIN и `retained` конверта.

Из локальной сети передаются только state и availability известных
устройств, `bridge/state`, `bridge/info`, `bridge/devices` и ответы на
разрешённые bridge-команды. Конфигурация, логи, discovery, неизвестные topics
и эхо команд не пересылаются. `bridge/info` формируется из необходимых
описательных полей: версия, coordinator, permit join и время его окончания.
Для согласованного профиля команд ADR-010 версия включает также номера
пакетов `zigbee_herdsman_converters.version` и `zigbee_herdsman.version`:
только эти строки, не вложенные объекты библиотек. Строки проверяются по
формату версии пакета и ограничены 64 символами. Неизвестная версия остаётся
неизвестной, не выводится из номера Zigbee2MQTT. Это совместимое уточнение
описательных metadata в прежнем конверте v1; существующие установки
передают эти поля только после добровольного обновления connector.
Вложенные конфигурации, MQTT-пароли и Zigbee network key исключаются.

MQTT-адаптер выполняет технический разбор и вызывает одну публичную
операцию `ZigbeeFacade`. Домен разрешает полное имя по своему snapshot
metadata и использует общую обработку состояния, истории и команд.
Адаптер не читает JPA и не принимает бизнес-решения. Вложенные имена
поддерживаются также в прямом Z2M-маршруте без конверта; неизвестные
подтопики свойств не превращаются в устройства.

### Команды и восстановление связи

Обратные topics сохраняют прежний формат: `<полное имя>/set`,
`<полное имя>/get` и разрешённые `bridge/request/*`. Команда проходит
только из namespace своего координатора к известному устройству.
Retained-команды отклоняются. При отсутствии любого соединения команды
не накапливаются и не повторяются автоматически после восстановления.
Неоднозначный результат не повторяется вслепую.

Локальная сессия не получает очередь сообщений предыдущего подключения.
Живые состояния не сохраняются в исходящей очереди на время обрыва облака;
после восстановления полученные из cache значения остаются сохранёнными.
Применение MQTT QoS и клиентских очередей обязано подтвердить это поведение
на стенде, включая сообщения в момент обрыва. Отсутствие свежих показаний
не отображается как подтверждённая живая связь.

Это изменение не даёт допуска к автоматическому поливу. Локальный таймер,
проверенная модель, однократный start и остальные требования ADR-007
сохраняются. Demo не создаёт внешние соединения или команды.

### Совместимое внедрение

Сначала публикуется backend, принимающий новый и прежний форматы.
Затем выпускается новый пакет connector и обновляются форма и инструкция.
Существующие connector, прямой Zigbee2MQTT и ПушОк продолжают работать
по своим контрактам; автоматического переноса или перезапуска нет.
Переход существующего пользователя выполняется только при добровольном
обновлении его локального пакета. Ограничение старого connector остаётся
явно описанным до такого обновления.

Перед production обязательны проверки:

- Простые, вложенные и допустимые Unicode-имена; добавление и переименование
  без повторного скачивания конфигурации; отказ при неоднозначных именах.
- Два координатора с одинаковыми именами и IEEE; запрет чужих namespace,
  эха, служебных payload и секретов.
- Сохранённые значения при первом старте и повторной подписке; обрыв каждого
  соединения; отсутствие старого состояния, выданного за новое измерение.
- Однократная передача команды, отказ retained-команд и отсутствие очереди
  команд при восстановлении; ошибки TLS и авторизации.
- Общие история и интерфейс, регрессия прежнего Z2M, ПушОка и native-маршрута,
  отсутствие внешних публикаций из demo; проверка упаковки и развёртывания.

## Последствия

Пользователь не меняет имена и сопряжение существующей сети. Новые устройства
и их показания проходят через общий домен без ручного редактирования списка.
Сохранённые показания сохраняют своё происхождение после облачного перехода.

Цена решения — поддержка небольшого процесса connector и двух версий
входящего MQTT-контракта на время совместимости. Условия восстановления
и запрета очередей нужно доказать тестами; этот ADR не выдаёт проектируемое
поведение за уже проверенную реализацию. Архитектурные описания и публичные
материалы обновляются вместе с кодом только после принятия решения.

Официальные источники: [Zigbee2MQTT: имена устройств](https://www.zigbee2mqtt.io/guide/configuration/devices-groups.html#generic-device-options),
[Mosquitto: мосты и маршрутизация](https://mosquitto.org/man/mosquitto-conf-5.html),

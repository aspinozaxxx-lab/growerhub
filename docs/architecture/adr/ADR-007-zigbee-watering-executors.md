# ADR-007: Zigbee-исполнители в общем сценарии полива

Статус: принято владельцем проекта 25 сентября 2026 года.

Поддержка Zigbee-полива выключена по умолчанию. Этот документ не разрешает управление физическим оборудованием
пилотного пользователя и не объявляет какую-либо модель клапана совместимой.

## Контекст

Первый кандидат на пробное подключение использует Zigbee2MQTT, Home Assistant
и клапаны полива. Существующий connector позволяет передавать их состояние
и историю. Однако встроенные ручной полив и сценарий `WATERING` работают
через native pump: это явно ограничено в `backend/domains/automation.md`
и проверяется `AutomationFacade.validateResource`.

Назначение клапана в слот света не является поддержкой полива: оно обходит
сессии, журнал, ограничения длительности и предметное назначение устройства.
Для перехода от просмотра данных к регулярной автоматизации требуется
расширение контракта. Конкретная модель, exposes и автономная остановка
клапанов кандидата пока не проверены.

Решение дополняет ADR-002, ADR-004, ADR-005 и ADR-006. Существующий MQTT-контракт
Grovika, её локальные ограничения и изоляция физической фермы сохраняются.

## Решение

### Один сценарий и один жизненный цикл

Сохраняется общий слот с внутренним именем `WATER_PUMP` и общий сценарий
`WATERING`. Пользователь видит назначение «Полив» и выбирает подходящий насос
или клапан. Нового домена, отдельного приложения и второй реализации сессий
не создаётся.

Слот допускает существующий `NATIVE_PUMP` либо `ZIGBEE_DEVICE`, для которого
backend подтвердил возможность ограниченного по времени полива. Backend
проверяет владельца, физический канал и доступные операции. Frontend получает
готовность и причину недоступности через REST; таблицы моделей в нём нет.

`automation` сохраняет размещение и настройки, формирует цель полива и
обращается к `pump`. Домен `pump` продолжает владеть сессией, снимком растений,
лимитами, остановкой и завершением журнала. Для Zigbee он использует публичные
контракты `zigbee`; прямых обращений к MQTT и чужой JPA нет. Сведения об
устройстве, его фактическое состояние и команда принадлежат `zigbee`.

### Адресация и совместимость

Сессия сохраняет неизменяемый тип и ссылку на исполнителя:

- native: прежний `pump_id` с существующими проверками устройства;
- Zigbee: координатор, IEEE устройства и управляемое свойство/канал.

Zigbee-клапан не превращается в фиктивную Grovika или native pump. Для него
добавляется явный вариант цели сессии. Существующие API с `pump_id`, данные
и идентификаторы остаются совместимыми. Пользовательские операции Zigbee-полива
адресуют проверенную привязку оборудования, а не произвольный MQTT topic.

На один физический исполнитель допускается одна активная сессия, независимо
от числа запросов и перепривязок. Ограничение native-устройства на одновременную
работу не ослабляется. Переназначение занятого канала проверяется сервером.

### Допуск к автоматическому поливу

Одного свойства `state=ON/OFF` недостаточно. Первая поддержанная модель должна
принимать ограниченную длительность и самостоятельно закрываться при потере
связи с GrowerHub. Возможности определяются из exposes и проверенной семантики
команды; соответствие названия модели само по себе не доказывает поддержку.
Конкретное преобразование команды фиксируется после получения модели/exposes.

Для допуска обязательна физическая проверка локальной остановки после потери
связи. Облачный таймер со второй командой `OFF` не считается её заменой.
Неподтверждённое устройство остаётся доступным для просмотра состояния и истории,
но не предлагается как готовый исполнитель сценария полива.

Сессия учитывает подтверждённое состояние. Потеря связи или неизвестный результат
остановки не отображаются как успешное завершение. После перезапуска backend
сначала восстанавливается и сверяется существующая сессия; новый полив вслепую
не начинается. Повтор команды не должен продлевать аппаратный предел работы.
Доступные режимы сессии ограничиваются проверенными возможностями исполнителя.

Без расходомера и заданной скорости объём остаётся неизвестным. Расчёт по
скорости явно отличается от измеренного расхода. Существующая семантика журнала
native-полива сохраняется, повторное завершение не создаёт дубликаты.

### Изоляция и внедрение

Маршрут PHYSICAL/SIMULATED выбирается по серверным данным согласно ADR-006.
Виртуальный клапан использует те же правила сессии, но не публикует физические
MQTT-команды. Совпадающий IEEE у разных координаторов не объединяет исполнителей.

Миграция только добавляет совместимые поля и ограничения. Настройки, назначения,
credentials и история существующей фермы не переписываются. Zigbee-полив
включается отдельным серверным параметром, первоначально выключенным. Никакие
старые слоты не конвертируются и сценарии автоматически не включаются.

До production обязательны проверки владения, конкурентного старта, отказа
команды, отсутствия свежего состояния, перезапуска, повторного завершения,
защитной остановки и нулевых физических публикаций из демо. Регрессия native
и демополива проходит на отдельной среде; рабочая ферма владельца не служит
тестовым стендом. Миграция и восстановление проверяются на копии базы.

### Параметры первой реализации

`zigbee.watering.enabled` (`ZIGBEE_WATERING_ENABLED`) по умолчанию false.
`verified-devices` по умолчанию пуст: физически подтверждённых моделей пока нет.
Запись допуска относится к конкретным публичному UUID координатора, IEEE и
state-property. Она содержит SHA-256 сериализованного JSON definition, точную
software-build-id, duration-property, on/off-value, max-duration-seconds,
duration-unit-seconds, verified-at, evidence-reference и подтверждение
`duplicate-command-does-not-extend-timer`. Доказательство должно описывать
физические испытания автономного закрытия и повторной команды; оно не заменяется
наличием exposes или тестовым fixture. Изменение definition/прошивки отзывает допуск.

Первая форма команды объединяет длительность и ON в одном payload. Другую
семантику конкретного устройства нельзя подключить одной записью без адаптации
и проверки. Start публикуется с QoS 0 без retain и не повторяется; OFF использует
QoS 1 без retain. Ограничение MQTT-клиента не заменяет проверку повторов bridge.
Живое состояние хранится отдельно от retained snapshot. Настройки свежести,
ожидания подтверждения и максимума виртуального таймера задаются в application.yml.
Режимы until-leak и pulse для Zigbee пока недоступны, защитный stop от протечки
сохраняется. Существующие теплицы и шаблон их назначений не конвертируются;
виртуальный клапан можно добавить и назначить в общем конструкторе.
Известный поливной канал не назначается в свет/климат; обычная команда ON
или изменение его таймера через общий control API отклоняется. Закрытие OFF доступно.

## Последствия

Меняются контракты целей сессий `pump`, готовности полива `automation` и
возможностей Zigbee-исполнителя. Назначение, ручной полив, автоматизация,
состояния и журнал используют общие страницы приложения. Архитектурные
описания доменов обновляются вместе с реализацией после принятия ADR.

Поддержка начинается с подтверждённой модели, затем расширяется по тем же
критериям. Пока такой проверки нет, пилот ограничен получением реальных
показаний и истории. Это промежуточный этап, а не выполнение всей цели
регулярной автоматизации.

Пакет connector для Home Assistant OS — отдельная задача доставки. Он не
добавляет поддержку полива сам по себе и не входит в это решение.

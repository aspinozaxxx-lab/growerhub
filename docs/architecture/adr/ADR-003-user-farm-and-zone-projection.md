# ADR-003: одна ферма пользователя и проекция теплиц

Статус: принято

## Контекст

Пользовательский интерфейс оперировал помещениями и вложенными секциями, хотя пользовательская модель требует одну ферму с теплицами, слотами ресурсов и растениями. Сценарный worker уже использует устойчивую иерархию `room → box`: кондиционер и комнатный климат принадлежат room, остальные ресурсы и сценарии — box. Прямая замена этой модели изменила бы проверенную логику автоматизации и MQTT-контракты.

Растение принадлежит домену `plant`, а его размещение и скорость полива — домену `automation`. Последовательные REST-запросы не обеспечивают атомарность создания или изменения растения вместе с размещением.

## Решение

- У пользователя может быть не более одной фермы.
- Ферма принадлежит домену `automation` и объединяет пользовательские rooms.
- В пользовательском контракте room является теплицей или зоной.
- У каждого room существует ровно один внутренний box. Box не входит в пользовательский REST-контракт и остаётся деталью исполнения worker.
- Пользовательская операция зоны атомарно распределяет слоты, растения и сценарии между room и его внутренним box.
- Пользовательский климат зоны атомарно сохраняет `BOX_CLIMATE` и `ROOM_CLIMATE`; worker и его конфигурация не меняются.
- Привязка одного физического канала допускается только к одному слоту. У Zigbee-устройства разные свойства считаются разными каналами.
- Домен `automation` оркестрирует создание, изменение и удаление растения с размещением через публичный `PlantFacade` в одной транзакции.
- Прямые sensor/pump-привязки к растениям не становятся источником конфигурации автоматизации.
- Административный контракт может показывать внутренние rooms и boxes для диагностики, но использует те же инварианты.

## Последствия

- Добавляется сущность farm и обязательная связь room с farm.
- Миграция V15 переносит существующие rooms в зоны одной фермы пользователя и создаёт отсутствующий внутренний box.
- Пользовательский REST получает проекцию `farm → zones` без внутренних box.
- Миграция V16 удаляет группы растений из схемы; `plant_group` отсутствует в домене, REST и frontend.
- После переключения frontend удаляются старые пользовательские room/section endpoints. Диагностический admin API сохраняется.
- Изменение развёртывается совместимо: сначала новый backend-контракт и V15, затем frontend, после этого V16 и удаление старых пользовательских endpoints.
- MQTT namespace, payload, worker, runtime state и история действий остаются без изменений.

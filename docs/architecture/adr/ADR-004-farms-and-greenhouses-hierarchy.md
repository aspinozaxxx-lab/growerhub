# ADR-004: Иерархия ферм и теплиц

Статус: принято

Заменяет: ADR-003

## Контекст

В пользовательской модели ферма означает помещение, а теплица — отдельную
установку внутри этого помещения, в которой находятся растения, датчики и
исполнительные устройства. У одного пользователя может быть несколько
помещений и несколько теплиц в каждом помещении.

До этого ADR пользовательский контракт добавлял отдельную сущность
`automation_farms`, показывал `automation_rooms` как теплицы и скрывал
`automation_boxes`. Такая проекция вводила лишний третий уровень и
ограничивала пользователя одной фермой. При этом исполнительная модель
`room → box` уже соответствует требуемым двум уровням.

Климатическая автоматика разделяет обнаружение перегрева и обработку запроса
на охлаждение. Теплица должна публиковать запрос при превышении порога даже
тогда, когда у неё и у родительской фермы нет кондиционера. Иначе пользователь
не видит проблему, которую пока нечем обработать.

## Решение

- `automation_room` является пользовательской фермой-помещением.
- `automation_box` является пользовательской теплицей и принадлежит ровно
  одной ферме.
- Пользователь может иметь любое количество ферм и теплиц.
- Ферма и теплица могут независимо иметь слот кондиционера.
- Остальные слоты растений, датчиков и оборудования принадлежат теплице.
- `BOX_CLIMATE` вычисляет запрос на охлаждение по температуре теплицы
  независимо от наличия кондиционеров и обдува.
- Локальный кондиционер теплицы может обработать её запрос. Необработанные
  запросы агрегирует родительская ферма и, если возможно, обрабатывает своим
  кондиционером.
- Если обработать запрос нечем, флаг запроса сохраняется в состоянии теплицы
  и отображается на пользовательском дашборде.
- Настройка имён, количества и связей ферм и теплиц выполняется только в
  разделе «Настройки → Зоны».
- Конструктор фермы выбирает существующую ферму, назначает оборудование и
  размещает растения, но не изменяет иерархию. Настройка и переключение
  пользовательских сценариев выполняются только на странице «Автоматизации».
- Внутренние значения `ROOM`, `BOX`, `ROOM_CLIMATE` и `BOX_CLIMATE` остаются
  неизменными. MQTT namespace и payload-контракты не меняются.
- Поле растения `zone_id` временно сохраняет имя для совместимости REST, но
  содержит идентификатор теплицы (`automation_box`).

## Миграция

Миграция V17 преобразует данные, созданные по ADR-003:

- для каждой строки `automation_farms` создаёт одну родительскую
  `automation_room` с именем фермы;
- существующие rooms-зоны преобразует в дочерние boxes-теплицы, сохраняя
  растения, ресурсы, сценарии, состояния теплиц и журнал действий;
- состояние нового родительского `ROOM_CLIMATE` worker вычисляет заново;
- прежний кондиционер зоны переносит в локальный слот теплицы;
- удаляет ограничение одного box на room, колонку `farm_id` и таблицу
  `automation_farms`.

## Последствия

- Публичный self-service API возвращает список `farms`, каждая из которых
  содержит `greenhouses`.
- Tenant isolation проверяется на каждом уровне и для администратора в обычном
  кабинете действует так же, как для любого пользователя.
- Удаление фермы оставляет её растения без размещения; удаление теплицы делает
  то же самое только для растений этой теплицы.
- Перемещение теплицы между фермами не изменяет её растения, слоты, сценарии
  и историю.
- Уникальность физического канала между слотами сохраняется.
- Административный API продолжает использовать внутренние названия room и box
  для диагностики.
